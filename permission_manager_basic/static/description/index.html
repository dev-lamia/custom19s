01
NAVIGATION CONTROL

Hide Menus/Submenu

SETUP UI PREVIEW  ·  Illustrated example

Choose the menus and submenus that should disappear for members of a policy.

WHAT YOU CAN CONFIGURE
  • Select the exact Menu Entry; its display label and parent menu are shown for clarity.
  • Set an optional Condition Domain for rule-specific applicability.
  • Switch a line on or off using its Active setting.
Example use: Keep selected configuration or accounting menus out of a trainee user's navigation.
Good to know: Menu hiding changes navigation visibility; use Model Permissions for operation-level restrictions.
02
OPERATIONS & VIEWS

Model Permissions

SETUP UI PREVIEW  ·  Illustrated example

Manage what members may do on an Odoo model and which model-level options appear.

WHAT YOU CAN CONFIGURE
  • Block Read, Create, Edit, Delete, Archive, Unarchive and Duplicate for a selected model.
  • Control Import Data, Export Data and spreadsheet operations.
  • Hide the model, Action menu, selected reports/actions, specific views, or view-switcher types such as List, Form, Kanban, Calendar, Pivot, Graph, Activity and Map.
  • Optional Condition Domain provides condition-aware model rules.
Example use: Allow team members to review sales records, but block deletion and duplication.
03
SEARCH EXPERIENCE

Search Panel

SETUP UI PREVIEW  ·  Illustrated example

Simplify the search controls available on the selected model.

WHAT YOU CAN CONFIGURE
  • Hide the full Search Menu, or configure Filters, Group By and Favorites separately.
  • Control Custom Filter, Custom Group By and Save Current Search options.
  • Configure a different set of search choices for each selected model.
Example use: Keep a simple search interface for new employees without advanced custom filters.
04
FIELD-LEVEL RULES

Field Controls

SETUP UI PREVIEW  ·  Illustrated example

Configure what a particular field looks like and how users can interact with it.

WHAT YOU CAN CONFIGURE
  • Choose a Model and Field, then set Hide, Read Only or Required as needed.
  • Use the Condition Domain for conditional attribute rules.
  • Choose applicable form, list, kanban and search view contexts.
  • Configure no-import / no-export settings and relational domain values in the field-rule form.
Example use: Make a sensitive price field read-only for selected staff, or require a field on a form.
Good to know: See the three Field Controls sub-tabs directly below for the individual configuration areas.
05
RECORD VISIBILITY

Record Domain Rules

SETUP UI PREVIEW  ·  Illustrated example

Filter which records policy members can see when viewing an Odoo model.

WHAT YOU CAN CONFIGURE
  • Select the Model and define a Filter Expression using an Odoo domain.
  • Optionally choose a Current User Field to restrict matching records to the signed-in user.
  • Read, Write, Create and Delete scope switches are present in the configuration.
Example use: Use a Read filter to display only opportunities assigned to the current salesperson.
Good to know: Read-scope filtering is verified in the module source. The other scope switches should be tested before relying on them as backend enforcement.
06
COMMUNICATION UI

Chatter Visibility

SETUP UI PREVIEW  ·  Illustrated example

Choose which Chatter controls appear on forms for each model.

WHAT YOU CAN CONFIGURE
  • Hide the entire Chatter section, or just the message composer.
  • Control Log Note, Schedule Activity and Search Messages.
  • Hide attachments, followers and the follow/unfollow button.
Example use: Keep an internal model form clean by hiding Chatter actions the team does not need.
07
FORM INTERFACE

Hide Buttons/Tabs

SETUP UI PREVIEW  ·  Illustrated example

Hide chosen form buttons and notebook tabs for the applicable users.

WHAT YOU CAN CONFIGURE
  • Pick a Model and click Refresh Available Items to discover its buttons and tabs.
  • Choose Hide Buttons and/or Hide Tabs from the available item lists.
  • Add an optional Condition Domain for more targeted UI visibility rules.
Example use: Hide an unnecessary workflow button or a sensitive configuration tab.
Good to know: This hides user-interface elements; it does not itself prevent a corresponding method being invoked by other routes.
08
POLICY-WIDE SETTINGS

Global Controls

SETUP UI PREVIEW  ·  Illustrated example

Set policy-wide restrictions and choose how the company scope is applied.

WHAT YOU CAN CONFIGURE
  • Apply regardless of company or select specific companies for policy scope.
  • Force Read-Only for applicable users.
  • Block Debug Mode or Block Login for applicable users.
  • Hide Export Available Fields in the export field browser.
Example use: Apply a read-only review policy within selected companies.
Good to know: Use Block Login and Force Read-Only carefully; these can interrupt users' normal work.
INSIDE FIELD CONTROLS

The 3 field-rule sub-tabs, explained

Open a field control line to configure the following areas.

Attribute Rule

Change individual field behavior

Hide Field, Read Only, Required, an optional Condition Domain, and Apply On choices for Form, List, Kanban and Search.

Use when a form field should be hidden or mandatory for a policy member.

Domain Rule

Configure relational selection settings

Select a Many2one/Many2many field and store its Selection Domain in the field rule.

Important: a runtime consumer that enforces this stored selection domain was not confirmed in the supplied module source; verify its behavior before relying on it.

Import / Export

Protect the selected field in data flows

Configure No Import and No Export for the selected model field.

Use to control field availability in supported import/export operations.

UNDERSTAND THE DIFFERENCE

Which setting should you choose?

Hide Menus

Controls where a user can navigate.

Model Permissions

Controls actions on an Odoo model.

Record Domains

Filters which records appear in supported read views.

Field Controls

Controls individual fields and their behavior.

Technical note: Form button/tab hiding and some search/chatter controls affect the user interface; do not confuse hiding a control with a universal backend access rule. Verify your policy in a test database with an affected non-administrator user before deploying restrictive settings.
